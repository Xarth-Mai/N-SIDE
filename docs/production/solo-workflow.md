# 个人开发：路线导航、工作循环与验收

本流程服务“作者判断方向与体验，Codex 主力设计实现”的工作方式。先用几句话解释当前要解决的问题，再通过小样和实际结果帮助作者判断；学习随任务进行，不把完成课程作为开始开发的前置

总路线图（`todo/demo-roadmap.md`）负责 M0—M7 目标与边界；细化进度（`todo/demo-progress.md`）负责当前完成数量、工作包与依赖；进度数据（`todo/demo-progress.json`）是工作包状态的唯一编辑源。已确认的长期设计仍按[项目约定](../conventions.md)写回所属 `docs/`，不在进度数据中复制整份设计

## 每次开始先知道在哪里

Codex 读取当前任务、进度数据、相关设计和最近证据，核对真实分支与工作区变更。优先执行用户明确指定的任务；没有指定时，继续已启动且能推进的工作包，再选择依赖满足的关注项。`focus` 是关注或建议入口，不代表这一项已经启动

开始时用以下格式说明，随后进入实质工作：

```text
阶段：M1 基础可玩原型；已验收 2/8
当前：M1-03 跟随镜头，清单第 3/8 项；第 2 轮，步骤 2/6「决策与设计」
目的：让玩家在狭巷与店内看清角色和目的地
这次需要你判断：两种镜头回正方式哪一种更舒服
我先交付：同一路线、同参数基线的两个可玩对照
```

这是格式示例，不是项目当前状态。若本轮只读或讨论，不启动 work，也不改变完成数。针对普通小修，只报告关联工作包和本次结果，无需重新展开全部路线

城市、Viewer、白天视觉与空间收口任务已按交付范围归档至 `todo/archive/`，剩余工作见总路线图的承接表。它们作为 M0 盘点、M1 人尺度验证、M4 品质样板的输入；没有匹配的游戏验收证据时，不折算为主线完成数。用户指定继续旧主题时，先读归档与承接表，在工作日志建立本次续接记录，按授权范围推进；不重开已结项记录，也不强行先完成全部 M0

## 三层粒度

| 层级 | 用途 | 展开深度 |
| --- | --- | --- |
| M0—M7 阶段 | 描述可交付的游戏能力与阶段出口 | 长期稳定 |
| M1-03 等工作包 | 一个可以单独判断、交付、验收的结果 | 全阶段列明决策、交付与通过条件 |
| 本轮动作 | 本次要看的资料、选项、小样、修改和测试 | 开始该工作包时展开；通常只详细计划当前与下一项 |

远期工作包不是不可更改的规格。M0 确认范围、M4 确认品质与成本、M5 冻结内容时复核它们；具体技术选型、UI 外观、数量与参数按原路线保留为待决或实验

## 进度怎么计数

`已验收 1/8` 表示该阶段八个稳定工作包中有一个 `done`，不是完成了八分之一的工时。`清单第 3/8 项` 只是当前工作包的位置。阶段最后一项是整体出口验收，单项都做完仍需要检查组合起来的体验

沿用任务状态：`backlog` 待安排、`ready` 可开始、`in_progress` 进行中、`blocked` 受阻、`done` 已验收、`cancelled` 已经作者批准移出范围。满足依赖的 `backlog` 会在看板上显示为可开始，不修改源状态

等待作者试玩的工作包保持 `in_progress`，其 `work.step` 为 `review`；缺少硬件或关键决定而无法推进时用 `blocked` 并记录原因。`done` 需要实际证据和符合工作包角色的验收记录。代码完成、文档存在、静态截图、构建成功分别只能证明各自覆盖的部分

Loop 做了几轮，不增加工作包完成数。范围取消不计为完成，也不从当前分母悄悄消失；它仍占原清单位置，单独显示“批准移出”。取消需要作者批准记录，阶段出口不能取消。新增或重分工作包时增加 `plan_revision`，保留原 ID，在工作日志解释旧／新分母、原因、替代项和批准来源

已验收结果被后续变化破坏时，重开受影响项为 `in_progress` 或 `blocked`，删除当前 `accepted`，旧记录留在日志。检查依赖它的后续项和阶段出口，必要时一并重开；只有实际受影响的证据需要重做。进度回退是如实报告，不用新子任务藏住已失效的验收

## 一个可重复的 work loop

| 步骤 | Codex 做什么 | 作者参与什么 | 本步结果 |
| --- | --- | --- | --- |
| 1 `orient` 定位与讲解 | 读现状和证据，解释本轮目的及一两个必要概念 | 补充真实目标或纠正理解 | 问题、范围、现有结论与本轮假设 |
| 2 `design` 决策与设计 | 给出推荐及最多两三个有意义的选项，说明体验和制作代价；形成线框、规则或小样计划 | 拍板影响体验、范围、成本的决定 | 本轮方案与事先约定的验收方式 |
| 3 `build` 制作 | 在已定边界内实现代码、数据、灰盒或资产接入，复用现有专业 skills | 仅在有真实创作判断时介入 | 可检查或可玩的版本 |
| 4 `verify` 客观检查 | 运行适用测试，检查引用、状态、构建和性能，修正明确问题 | 提供缺少的实际测试环境时协作 | PASS／FAIL／NOT RUN 及真实日志 |
| 5 `review` 体验／作者验收 | 给出具体启动方式、走查路线、最多三个观察问题，归纳反馈 | 操作、观察、选择并反馈；需要陌生玩家的项安排真实试玩 | 通过、修订或缺少证据的判断 |
| 6 `record` 记录与下一步 | 更新设计、证据、进度和看板；给出下一项或下一轮要改变的假设 | 确认新的范围变化或阶段放行 | 可跨会话续接的记录 |

工作包类型为 `decision` 时，交付可能主要是批准的方案；`delivery` 侧重客观实现；`loop` 需要比较和反复试玩；`gate` 审核阶段整体。这些工作均可使用同一流程，但无需为不适用步骤制造空文件：在记录中简要说明“不适用及原因”

客观检查之后的真实运行、capture、状态断言和画面自查统一遵循[运行验证](runtime-validation.md)。专业原版 Skills 与项目差异由 `.agents/skills/nside/` 路由，资产继续使用[现有清单](assets.md)，不在各 Skill 中重复保存状态

迭代次数开放，记录“第 2 轮”，不写“2/3 轮已完成”。反馈未通过时保留证据、提出新的小假设，再进入下一轮；不推倒已成立的部分。在授权范围内依据新证据继续定位与修复；重复失败且无法取得新证据时，报告具体阻碍和所需输入。涉及作者选择或实际手感时暂停等待真实反馈，不替作者批准，不声称后台继续工作

## 制作型 Loop 的批次进度

M5 的场景、角色、UI、声音不是无限打磨同一对象，而是按已批准清单逐件或逐批生产。先在 M5-01 确认清单与来源，再在相关工作包记录中维护对象 ID、名称、制作状态、证据和实际验收结果。每个清单只有一个主记录，其他地方通过引用展示

例：`M5 已验收 2/8；当前 M5-05 UI 制作；页面已验收 4/9；对话面板第 2 轮／步骤 5/6。` 数量仅为显示示例，实际页面数由已批准 UI 范围确定，不预先把 9 个页面当成需求

一个对象的流程是：需求与规格 → 制作 → 接入实际构建 → 检查 → 实际验收。模型导出、UI 静态图和一段音频的完成，只代表相应工序，不代表它在游戏里已交付

已完成与取消的工作包仍保留在进度数据中，保持 ID、分母和依赖稳定；独立任务关闭后移入 `todo/archive/`，同步更新引用

当前进度工具只确定性统计工作包，不解析任意格式的批次表；Codex 从该工作包链接的清单读取批次进度，不在 JSON 中再手填另一套重复数量。每个工作包只有在范围内所有必交批次完成并通过整体验收后才计入阶段 done

原型型 Loop 用同一场景比较假设；制作型 Loop 按固定方法处理清单；问题修复型 Loop 从缺陷记录出发、复现、修正并回归。这三种 Loop 共用六步工作流，不需要三个独立调度系统

## 作者与 Codex 的分工

作者保留体验方向、角色与故事选择、范围和成本、主观品质、阶段放行与发布决定。一个真实反馈或一次集中评审可以覆盖多个工作包，分别链接同一记录；工作包数量不是需要向作者提问的次数。Codex 对已授权范围内的实现细节自主推进，承担资料核对、设计草案、代码和数据、工具与自动检查、问题定位和记录

遇到待决问题，先在仓库和现有记录找答案；已有决定直接沿用。必须询问时只处理眼前阻塞：解释它影响什么，给出推荐，让作者做判断。不要一次抛出全部阶段的问题，不把作者变成文件和函数审批员

`reviewer` 指这项结果需要谁提供验收记录：`author` 是作者判断，`codex` 是有实际执行证据的技术检查，`playtester` 是真实试玩记录。角色字段不是身份认证，也不是能自动证明游戏好玩的机制；记录必须来自真实行为。所有阶段出口都由作者放行

## 状态与证据如何落盘

Codex 维护 `todo/demo-progress.json`。每个工作包的决定问题、交付和通过条件是计划；`status`、`work`、`evidence` 和验收记录是现状。详细测试、作者反馈与迭代历史保存在工作日志（`todo/demo-worklog.md`）或已有任务的证据文件，不复制完整聊天、不公开无关个人信息

需要反复迭代时，增加如下字段；以下为格式示例，路径、轮次与输入版本应替换为真实记录：

```json
{
  "status": "in_progress",
  "work": {
    "round": 2,
    "step": "review",
    "record": "todo/demo-worklog.md#m1-03-r02",
    "next_action": "请作者按记录路线比较两种镜头回正方式"
  },
  "evidence": ["todo/demo-worklog.md#m1-03-r02"]
}
```

记录使用仓库相对路径。Markdown 证据引用使用显式锚点，例如 `<a id="m1-03-r02"></a>`，便于检查器验证位置。实际记录包含输入提交或校验和、构建、环境、操作方法、结果、未测项目、作者或试玩者反馈及下一步；引用截图的同时说明截图不能证明的操作项

通过后设置 `status: done` 并增加 `accepted`：`role` 与工作包 `reviewer` 相同，`by` 是实际审核者，`revision` 是此次被验收输入的提交／校验和，`record` 指向明确的验收记录，`result` 为 `pass`。若保留最后一个 `work`，其步骤应为 `record`。简单技术交付不必建立空的轮次记录，直接引用真实测试结果即可

范围取消使用 `status: cancelled`、具体 `reason` 和结构相同的 `scope_change`；其中 `role` 必须为 `author`。检查器可验证文件、锚点、状态和角色字段，但无法认证人的身份或测试真实性，这仍由实际审核负责

## 三个入口 skills

| Skill | 触发情境 | 负责什么 |
| --- | --- | --- |
| `n-side-guide` | 现在做到哪、下一步、继续项目、当前要学什么 | 核对进度、依赖与上下文，解释当前问题，选下一步 |
| `n-side-work-loop` | 开始／继续指定工作包、根据试玩反馈修改 | 执行一轮决策—制作—验证—反馈，维护续接记录 |
| `n-side-review` | 验收、这一项是否完成、能否进入下一阶段 | 核对证据、实际反馈和影响范围，决定是否可结项或待补证据 |

现有 `create-case`、`create-content`、`review-narrative` 继续负责专业叙事工作，由当前工作包按需要组合使用。导航 skill 不重复编写另一套叙事流程，不为每个阶段新增一个几乎相同的 skill

在 Codex CLI 或 IDE 中可显式使用 `$n-side-guide`、`$n-side-work-loop`、`$n-side-review`；也可直接说“继续 N:SIDE，先告诉我在哪一阶段和接下来要判断什么”。这些是项目内的指令工作流，不是常驻进程，也不保证未经检验的隐式路由永远正确

## 命令与验证

从仓库根目录运行，命令可直接用于 fish；从 `game/` 等子目录开始时，先用 `git rev-parse --show-toplevel` 定位根目录再执行：

```sh
bun run roadmap
bun run roadmap --stage M0
bun run roadmap --json
bun run roadmap:sync
bun run check:roadmap
```

`roadmap` 只读，显示已验收数与下一可推进项；`roadmap:sync` 从 JSON 生成 Markdown，不改变源进度。`check:roadmap` 检查格式、ID、依赖环、前置状态、证据路径、批准记录和看板是否同步，不运行游戏，也不自动确认作者体验

检查器使用 Python 标准库，与现有 Python 检查工具一致，通过 Bun 脚本统一入口，无新增第三方依赖。测试随 `bun run test:tools` 中的 unittest 自动发现；也可单独执行：

```sh
python3 -B -m unittest discover -s tools/tests -p test_roadmap.py
```

## Codex 引导行为的验收

工具单元测试与 skill 行为测试分开。接入后在实际 Codex 会话核对以下场景，并将观察记录到工作日志，未执行前标记 NOT RUN：

| 输入场景 | 期待行为 |
| --- | --- |
| “我们现在做到哪？” | 读取最新进度，仅报告位置、证据与下一项，不改状态 |
| “继续 N:SIDE” | 续接当前 work 或依赖满足的关注项，先简要解释，不重问已定设定 |
| “继续白天视觉样板” | 读取归档与承接项，在新记录中继续指定工作，不误报 M4 完成 |
| “UI 代码写完了，标记通过”但没有操作验收 | 指出缺少的具体证据，保持进行中，给出最短试玩路线 |
| 收到真实镜头反馈 | 归纳具体问题，只修改相关假设，新增一轮记录，不自动增加完成数 |
| “进入 M4”但 M2／M3 尚未通过 | 展示具体依赖缺口，推进可执行前置，或记录获授权的范围变化 |
| 同一需求已在 docs 确认 | 引用并沿用，不再次启动访谈 |

行为检查应覆盖根目录和从 `game/` 启动 Codex 的发现行为。无法运行 Codex 或没有图形环境时，如实保留 NOT RUN
