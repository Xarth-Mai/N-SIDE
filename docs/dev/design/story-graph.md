# 故事关系与连续性审查

[故事时间轴](../../player/story/index.md)收录全部十条主线与八条可选街坊故事。[quests catalog](catalogs/quests.json)是身份、阅读顺序、故事归属和跨任务关系的维护源；正文仍由各故事页面保存，人物与空间继续使用原有目录

## 数据职责

`story.role` 区分 main / side，原 `type` 保持玩法类型；`act` 与 `display_order` 表示阅读位置，`placement` 允许支线跨阶段。`status` 是文档设计状态，不参与条件计算，也不导出到玩家 Wiki

`required` 是带 `scope` 的门槛数组，`start` 限制开始，其他名称只限制相应阶段。`required_for_completion` 明确该阶段是否为任务完成必经，开始门槛必须为 true；米娜来信重访为 false，不把可选片段升级成尾声的完成要求。每个 `condition` 为递归 `all` / `any` 或类型化叶子，叶子必须写 `type`、`quest_id`、`target`、`value`、`reason`。空门槛数组表示尚无已登记的跨任务锁，不宣称任意时刻都可进入所有地点

`recommended` 只记录来源任务、理由和依据，不参与可进入性；`related` 记录无序的剧情联系，反向查看由系统生成，双方不重复抄写同一关系。当前只保留人物延续、伏笔、回收、事件后续、场所变化、主题呼应和历史补证七种语义

`outcomes` 为尚无 narrative 文件的章节登记正文明确交付的成果，记录类型、值、可读名称、出处与可选生产阶段 `gate`。例如第六章岸线判断只有在取得第五章原始记录后才能产出；任务开始不代表所有阶段成果可用。这些键是正文成果的设计索引，不是已经接入游戏的存档变量

beat 条件表示该节点的动作已经完成；仅进入节点不视作成果交付。已有 `narrative` 的任务从原文件解析 beat、information、delivers 和 state_changes，不再登记第二套 outcomes。信息条件要求对应认知值确有交付者；state、地点开放与角色关系条件同样必须指向已有声明。新章节细化 narrative 时迁移其成果引用，不能两处并存。当前没有有依据的跨章地点或人物关系硬锁，因此不为了展示类型而新增剧情事实

## 条件与推演

例如“完成 A，并且完成 C 或 D 中任一个”写作 `all: [A, {any: [C, D]}]`。反向影响由叶子查询生成：A、C、D 都影响目标，但勾选 A 后仍显示 C / D 的选择树，不显示任务已经解锁

Wiki 默认只显示设计关系。开启条件推演后，勾选的是临时假设成果，没有存档接入或本地持久化。完成整个任务不自动生成任意分支结果，也不把达到某个 beat 等同于之后的全部信息或状态。门槛满足只表示该门槛在假设下成立

实际十八条故事目前没有足以确定的跨任务 ANY 替代来源，因此数据保留真实条件；嵌套 ALL / ANY 的行为由构造案例测试。集中会谈是第七章正文允许的补充方式，但缺少具体 beat，不虚构一个已经实现的补课任务

## 逐篇审查的来源与维护

下方完整十八篇审查由 Wiki 准备流程从 catalog 的 `story.review`、强制条件、推荐与关系生成，后续影响反向推导。原始 Markdown 不再复制逐篇任务清单；主线目录、街坊目录、侧栏和十八篇正文的关系详情使用相同投影。新增故事须登记 catalog 并补齐正文，构建前检查失败时不发布不完整图

玩家投影仅包含标题、摘要、正文路由、可读条件、推荐与关系，剔除 review、内部状态键、beat ID、narrative 路径及设计状态。审查依据和作者问题保留在开发资料；完整正文已含结局，时间轴延续既有剧透范围

## 连续性问题与最小改动建议

| 项目 | 事实与状态 | 问题或不确定性 | 最小改动建议 |
| --- | --- | --- | --- |
| 人物认知 | 序章有米娜请求，第一章 B001 再次倾听 | 完整版可能重复首次求助演出，Demo 本身需要完整入口 | 完整版 B001 承认已听过简短请求，再问具体观察；Demo 保留完整介绍 |
| 首次会面 | 阅读支线允许遥提供当前编辑意见，第五章先介绍编辑再揭示历史 | 先玩支线时第五章不能装作从未交谈；支线不得提前泄露病程 | 第五章增加“此前谈过稿件”称呼分支；支线仅使用编辑身份 |
| 环境时序 | 晚场支线只写正常演出，第二章包含停用与恢复 | 未明确晚场在异常前还是恢复后，不能擅自设置硬锁 | 作者选定恢复后版本并用恢复状态限定，或允许异常前后两个普通晚场版本 |
| 可跳过体验 | 第八章运用前几章学到的规律，第七章允许集中会谈补齐 | 允许独立调查时，集中会谈是否包含可操作复习尚未定义 | 第七章增加三种局部行为的受控复习节点；也可明确主线调查必经，但不把生活支线改成必需 |
| 环境变化 | 第七章明确旧输出仍处置有效，第八章再次出现局部行为 | 仅看熟悉形体可能误读为前次帮助无效 | 新联动入口说明旧点已隔离，标出新自然通路；保留原处置状态 |
| 后续对白 | 尾声有米娜消息、渡口恢复等共同经历 | 没体验某调查时，不应使用亲历口吻；不是所有后续都需要锁住尾声 | 各重访片段检查具体成果；未亲历版本用授权近况，米娜消息使用 B016 条件 |
| 维护与照片 | 拍照支线有修好栏杆，未指定维护事件 | 若默认对应最终险情，会提前宣告处置结果 | 保留普通维护语义，若指定最终险情则只限制对应拍摄场景 |
| 可选支线 | 拍照拒绝与完全不参与都不影响主线成功 | 未发现当前主线必须依赖八条生活支线的证据 | 保持主线现场记录和集中会谈来源；不给可选照片、饭局、阅读设置主线硬锁 |

以上是已识别的连续性风险与最小方案，未擅自修改故事设定。作者需要决定晚场的时点、重复会面对白与最终行动的复习方式；细化制作时补齐阶段节点和场所状态，不影响现在阅读与维护关系图

## 自动检查边界

`bun run check:story-graph` 检查完整字段、任务引用、强制自依赖、顺序、条件混用、剧情引用、beat / information / state 成果存在性、来源标题、阶段产出、不可进入循环及可选支线硬依赖。可进入性按最小不动点计算，ANY 有外部入口时不误报为死循环；再次排除所有可选支线计算主线路径

跨任务检查证明声明层存在进入途径；同一任务内部路径、信息变更和互斥分支由 `bun run check:narrative` 检查。它不证明两个随时间变化的状态可同时成立，也不替代引擎存档与真实试玩。新增互斥状态跨任务组合时须提供运行状态验证，不能把结构可达性当作运行可达性

测试包含嵌套 ALL / ANY、部分满足、反向影响、无入口循环、有替代入口循环、阶段循环、错误目标、可选支线无替代依赖和公开投影。双站构建同时检查发布边界
