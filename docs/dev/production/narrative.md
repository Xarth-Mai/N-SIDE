# 叙事创作

## 设计单位

故事同时设计三层内容：戏剧中的目标、动机与变化；玩家实际进行的动作；信息的获得、推测与重新理解

**一个主要 Beat = 戏剧变化 + 玩家行动 + 信息变化 + 游戏状态变化。**

世界真相描述实际发生的事，角色认知描述人物知道或相信什么，玩家认知描述各节点形成的理解。关键发现可以改变目标、策略、关系或操作方式

## 逐步制作

| 阶段 | 产物 |
| --- | --- |
| Pitch / Logline | 一句话故事、当事人处境、玩家目标与独特行动 |
| Synopsis | 从开场到结局的完整因果与人物动机 |
| Treatment | 可玩序列、进入与离开状态、分支、资源需求 |
| Beats | 逐节点的行动、信息、状态与连接 |
| Greybox | 可实际完成的代表性路线 |
| Scene / Dialogue | 场景意图、角色表现、对白与演出 |
| Integration | 场景、声音、状态、存档与反馈接入 |
| Playtest / Revision | 观察玩家理解与行动，修改对应设计 |
| Content Lock | 内容交付与检查记录，进入翻译和录制批次 |

Pitch、Synopsis、Treatment 与场景规格放在任务的 `development.md`；结构状态放在 `narrative.json`；正式台词放在 `dialogue.csv`

日常片段采用“生活情境 → 玩家互动 → 灰盒 → 表演与声音 → 试玩”的流程。短委托按规模合并阶段

## 节奏与转变

故事从具体处境建立问题，让调查逐步加深理解，再由玩家行动推动解决。转折既改变对事件的解释，也改变下一步的目标与做法；人物的转变通过选择、行动及其后果呈现

每段节奏落实到可玩的节点：玩家在做什么、看到了什么、因此作出什么判断，以及场景和关系如何响应。安静的日常、发现线索的停顿与遭遇危险的压力共同组成体验

调查型委托可从 12–18 个主要 Beats 起步：开场建立异常与主动目标，中段改变解释，后段产生行动压力，结尾用新的理解处理问题并呈现余波。数量与时长随灰盒和试玩调整

## 协作与修订

叙事设计负责结构、信息与玩家体验；写作负责人物声音与对白；关卡与任务设计负责空间和行动；程序负责状态与接入；美术、声音与表演共同完成呈现

试玩问题回到最早承载它的资料：因果改大纲，线索顺序改 Beats，路线改关卡，人物表达改场景与对白，状态恢复改实现

一个完整委托的目录见[任务入口](../design/quests/index.md)，结构数据见[数据格式](../engineering/content-contracts.md)，实际观察见[试玩](../validation/playtesting.md)

## 输入、前提与样板

入口使用 `create-case`、`create-content` 和 `review-narrative`。先读相关百科、已确认的世界规则、人物知情范围、场所开放边界、当前委托规格与任务，不从空白重新设计已定设定。完整故事归玩家百科；开发稿引用故事后只补玩家行动、信息顺序、状态、资源和恢复，不复制另一份故事正文

本项目样板为[《最后的玩具》](../design/quests/QST-002/README.md)，其中[完整故事](../../player/story/main/last-toy.md)、[行动与恢复规格](../design/quests/QST-002/development.md)和[Demo 范围](../design/quests/QST-002/demo-scope.md)分工明确。候选优先细化与玩法已经接入是不同状态，静态 `narrative.json` 检查不证明游戏能执行这些条件

## 从行动与信息到实现

1. 列明委托人、受影响者、梦主、潜梦者、接应者与 Agent 的本次职责，区分作者知道、角色知道与玩家已观察的信息
2. 沿因果链写出困扰、形成与维持条件、现实影响、可验证线索、判断变化、处理动作和现实后果；将其链接到百科事实，不用一句解释跳过玩家应做的观察
3. 对每个 Beat 写进入条件、玩家动作、可见信息、状态变化、退出与补充路径；调查顺序允许变化时逐条核对必需线索与防死锁规则
4. 分开世界事实、玩家认知、本轮尝试与持久进度；读取、交付、取消、主动退出、失败重试和读档各自明确提交时机，稳定 ID 继续由现有对象和数据维护
5. 用实际可达空间安排线索、对白与表演，确认人物为什么在场、能说什么、离开后能否重访；未知的引擎变量或新条件先完善[内容契约](../engineering/content-contracts.md)，不把未支持字段写成已可执行
6. 先跑结构检查，再接入真实灰盒与对应恢复测试；试玩记录目标、因果、路线或表达问题，回到最早承载问题的资料修订

《最后的玩具》的“收集者并非最初判断的破坏者”应由保留室和运输信息改变玩家理解；实物移动的路径、数量与痕迹遵循正式故事，梦中增生不能在实现中变成现实物品无限发放。具体动作与状态以该委托开发稿为准

## 输出、检查与失败处理

交付更新后的规格、必要的节点/台词/资产关系、真实实现入口与任务证据。正式台词存在时才建立对应 `dialogue.csv`，演员与音频继续用稳定台词 ID；不为填满模板生成尚无用途的空数据

以下 fish 命令从仓库根执行，覆盖结构、对象和文档关系

```fish
bun run check:narrative
bun run check:story-design
bun run check:docs
```

字段、ID、引用、信息条件或分支断链失败时先修源数据；数据格式不支持所需规则时明确记录工程缺口，不能为通过检查删掉必要条件。真实操作中发生线索丢失、重复提交或无法退出时，修状态和恢复实现后复验；对故事因果或人物解释的疑问回到正式事实核对，只有冲突确实改变已定设计时交作者判断

结构 PASS、运行 PASS 与玩家理解分别记录。运行尚未接入时只交付设计和静态结果，真实流程与试玩保留 NOT RUN；一次文档制作完成不增加游戏能力完成数

## 《最后的玩具》制作样板

完整故事见[主线第一章](../../player/story/main/last-toy.md)，已选择的 Demo 范围见[制作范围](../design/quests/QST-002/demo-scope.md)，具体节点与恢复规则见[委托开发稿](../design/quests/QST-002/development.md)；本示例说明调查与行动共同构成转折的制作方法

## 可玩结构

检查房间与箱封 → 进入梦境追踪 → 看见收集者归还玩具 → 隔离收集者或跟随运输线 → 观察运输与货架变化 → 回现实核对拆箱痕迹、周转箱与夹层 → 再入梦恢复运输并创造处置窗口 → 现实接应解除有害联系 → 帮助米娜执行自己的随身物与收纳物选择 → 观察现实后续

隔离路线通过运输中断显现后果；跟随路线通过检查运输过程发现原因。两条路线使玩家理解同一规则，再据此改变行动

## 信息与体验

箱封、日期和照片说明反复打包；归还动作改变对收集者的判断；运输与货架的联动呈现维持机制。结尾通过整理行李表达携带记忆继续生活

试玩关注归还动作是否看清、拆箱与增生的因果是否理解，以及玩家能否说明自己的操作带来了什么

## 主线信息获取约束

重要事实至少有两种不同来源，其中至少一种经过玩家行动获得。玩家提前推断正确时，角色承认并推进验证；错过可选展示时，由受控记录、再次会谈或已知人物提供补充路径。可选支线丰富关系，不承担主线唯一必需证据
